01Inside the applicationWhat runs, where data lives, and which module owns each decision.

What are the runtime pieces? The browser and one local Node.js service share a loopback origin. SQLite and the operating system credential store have different jobs.

Implemented

Presentation

Home, Portfolio, Breakdown, Explore, Development and Data & connections use local API responses. Fund and security pages expose contributions and provenance.

Implemented

Calculation

Saved broker bids value supported positions. Decimal arithmetic applies compatible constituent weights. Exact ISIN matching comes first; company relationships require separate evidence.

Implemented

Persistence & recovery

SQLite retains accepted snapshots, source evidence and operation outcomes. Replay checks saved evidence. A failed source refresh keeps the last good result and exposes its age.

Code: main.tsservice.tsstore.tsoverview.tsweb/main.tsx

What does the current design still couple?

The refresh service accepts an injected provider list, while store/replay decoding defaults to the bundled registry. Broker-specific interpretation still reaches valuation code. Views use internal read types and explicit application routes. The shared registry, normalized broker boundary and view contracts are incremental work, not existing isolation guarantees.

V1's Python engine, Tauri shell, Supabase Hive and old root scripts are historical. They are not runtime dependencies of the local V2 application.

Two inputs meet at calculation
Broker lane
Connect → fetch positions / quotes → commit accepted snapshot → position value + quote date
Composition lane
Publication → evidence checks → select compatible source → constituent weight + date + ISIN
Core join
Exact fund selects the composition. Exact security ISIN joins direct and indirect contributions. An evidenced issuer relationship can group distinct securities separately.
Read model
Per-currency subtotals + contribution ledger + source dates + coverage/gaps → application views.
Indirect value = saved ETF position value × weight ÷ 100

The formula is simple. Knowing whether that weight measures the held fund and the intended exposure is the harder decision. No normalization of incomplete weights, no name/ticker merge and no second currency conversion.

Three different questions must stay separate.

Did we acquire the source? Can its rows support this measure? How much of the portfolio can we assign with valid identities and valuations? Downloading every row only answers the first.

Where should an extension live? One plugin identity can contribute a provider and a panel. Each capability gets only its relevant context; the core keeps the financial decisions.

Implemented at code baseline

Existing composition boundary

A typed provider manifest, bounded HTTP context, acquisition result and decoder serve the bundled iShares module. Core validates the candidate and calculates exposure. Duplicate providers and incompatible contracts are rejected.

ContractBundled registry

Still application-specific

Trade Republic uses a broker abstraction but some provider interpretation remains in valuation. Views are explicit application components. A shared multi-capability descriptor, installed-plugin isolation and public SDK are not present in this baseline.

BrokerNavigation

Concrete seam being repaired:

The same registry must reach acquisition, persistence and restart replay. The second provider must work through that registry, including inspection-only observations, without adding issuer formats to financial logic.

In progress · phases 1–2

Shared foundation + Amundi

One descriptor/registry across refresh, save and replay. Persist and inspect the substitute basket without treating it as Indian economic exposure. Prove failures and an independent provider.

Next · phase 3

View and broker proofs

One plugin contributes a provider and a useful panel. Then prove normalized broker observations and connection isolation. Views preserve the same coverage model.

Later · phase 4

Contributor package

Publish the exercised SDK, conformance checks and “operate / extend Prism” agent skills. Broader distribution follows working boundaries.

Module boundaries are not a security sandbox.

Bundled plugins run as reviewed application code. Independently installed code needs enforced isolation and permissions before it can be advertised as safe. No general plugin loader, marketplace or microservices are required for the current phases.
